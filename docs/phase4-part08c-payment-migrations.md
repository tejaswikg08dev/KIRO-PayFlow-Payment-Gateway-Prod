## 1. What's New in These Migrations

| New Concept | Where | What It Means |
|---|---|---|
| **`VARCHAR(30) PRIMARY KEY`** | Orders, Payments, Refunds | String IDs instead of UUID (for prefixed IDs like `order_abc`) |
| **`NUMERIC(19,4)`** | Amounts | Higher precision than merchant's `DECIMAL(5,2)` |
| **`CREATE TABLE IF NOT EXISTS`** | All tables | Safety — doesn't fail if table already exists |
| **Partial Index** | V1: `WHERE status = 'CREATED'` | Index only relevant rows (speeds up expiry queries) |
| **Composite Index** | V1, V2: `(merchant_id, status)` | Two-column index for dashboard queries |
| **`BIGSERIAL`** | V3: payment_methods | Auto-increment Long (PostgreSQL equivalent of IDENTITY) |
| **No `ON DELETE CASCADE`** | V2, V3, V4 | FK without cascade — payment records are never deleted |
| **No `updated_at`** | V4: refunds | Immutable records don't need update tracking |
| **`TIMESTAMPTZ`** | All tables | Short for `TIMESTAMP WITH TIME ZONE` — same as merchant |

## 3. Step-by-Step: V1 — Orders Table

**File:** `src/main/resources/db/migration/V1__create_orders_table.sql`

### Line-by-Line

```sql
-- V1: Create orders table
-- Stores payment orders created by merchants
```

SQL comments for documentation.

```sql
CREATE TABLE IF NOT EXISTS orders (
```

**🆕 `IF NOT EXISTS` — NEW vs Merchant**

Merchant migrations used `CREATE TABLE merchants (...)` (no IF NOT EXISTS). Payment adds this safety check.

| Without IF NOT EXISTS | With IF NOT EXISTS |
|---|---|
| Second run → ERROR: "table already exists" | Second run → silently skips (no error) |

**WHY?** Flyway normally prevents re-runs (tracks in `flyway_schema_history`). But `IF NOT EXISTS` is a safety net for edge cases (manual DB manipulation, testing).

```sql
    id              VARCHAR(30)     PRIMARY KEY,
```

**🆕 `VARCHAR(30)` PK — NOT UUID**

| Merchant migrations | Payment migrations |
|---|---|
| `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` | `id VARCHAR(30) PRIMARY KEY` |
| UUID auto-generated by PostgreSQL | String set by application (no DEFAULT) |

**WHY VARCHAR(30)?**
The ID is generated in Java code: `IdGenerator.generateOrderId()` → `"order_7a3f9b2c1d4e"` (18 chars). VARCHAR(30) gives room.

**WHY NO `DEFAULT`?**
Unlike UUID (generated by DB), prefixed IDs are generated in Java. The DB just stores whatever the application provides.

```sql
    merchant_id     VARCHAR(30)     NOT NULL,
```

Which merchant created this order. NOT a FK to merchants table — that's in a different database (`payflow_merchant`). Cross-database foreign keys don't exist in PostgreSQL.

**WHY NOT A FK?**
```
payflow_payment DB:  orders.merchant_id = "uuid-merchant-123"
payflow_merchant DB: merchants.id = "uuid-merchant-123"

These are in DIFFERENT databases. PostgreSQL can't create a FK between databases.
Application code ensures consistency (PaymentService validates merchant exists via Feign call).
```

```sql
    amount          NUMERIC(19, 4)  NOT NULL,
```

**`NUMERIC(19,4)` — PostgreSQL equivalent of Java's `BigDecimal(precision=19, scale=4)`.**

| SQL Type | Java Type | Same? |
|---|---|---|
| `NUMERIC(19,4)` | `BigDecimal` with `@Column(precision=19, scale=4)` | ✅ Yes |
| `DECIMAL(19,4)` | Same as NUMERIC in PostgreSQL | ✅ Yes (synonyms) |

PostgreSQL treats `NUMERIC` and `DECIMAL` as identical. Both store exact decimal numbers.

```sql
    currency        VARCHAR(3)      NOT NULL,
```

ISO 4217: `"INR"`, `"USD"`, `"EUR"`. Always 3 characters.

```sql
    status          VARCHAR(20)     NOT NULL DEFAULT 'CREATED',
```

**`DEFAULT 'CREATED'`** — New orders start in CREATED state. If the application forgets to set status, the DB sets it.

Maps to: `OrderStatus.CREATED` enum in Java.

```sql
    customer_email  VARCHAR(255),
    description     VARCHAR(500),
    receipt_number  VARCHAR(100),
```

**No `NOT NULL`** — all three are optional.

```sql
    expires_at      TIMESTAMPTZ,
```

**🆕 TTL COLUMN**

Set to `NOW() + 30 minutes` when the order is created (in Java code). Used to determine if an order has expired.

**No `NOT NULL`** — technically could be null (but the service always sets it).

**No `DEFAULT`** — unlike `created_at`, the expiry time is calculated in Java (not DB) because it's business logic (30 minutes might change to 60 minutes in the future).

```sql
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
```

Same timestamp pattern as merchant. `TIMESTAMPTZ` = `TIMESTAMP WITH TIME ZONE` (short form).

### Indexes

```sql
CREATE INDEX idx_orders_merchant_id ON orders(merchant_id);
```

**Query:** "List all orders for merchant X" → `WHERE merchant_id = ?`

```sql
CREATE INDEX idx_orders_status ON orders(status);
```

**Query:** "Find all CREATED orders" (for expiry check) → `WHERE status = 'CREATED'`

```sql
CREATE INDEX idx_orders_merchant_status ON orders(merchant_id, status);
```

**🆕 COMPOSITE INDEX — NEW CONCEPT**

A **composite index** covers TWO columns together. It's used when you query by BOTH columns at once:

```sql
-- This query benefits from the composite index:
SELECT * FROM orders WHERE merchant_id = 'mer_123' AND status = 'PAID';

-- Without composite index: PostgreSQL scans merchant_id index, then filters by status
-- With composite index: PostgreSQL finds the exact rows in ONE lookup
```

**WHY NOT JUST TWO SEPARATE INDEXES?**
```
Two separate indexes:  idx_merchant_id + idx_status
  → PostgreSQL uses ONE index, then scans the other condition row-by-row
  → Slower for combined queries

One composite index:   idx_merchant_status(merchant_id, status)
  → PostgreSQL finds exact rows matching BOTH conditions in one B-tree lookup
  → Faster for combined queries
```

**COLUMN ORDER MATTERS:** `(merchant_id, status)` means:
- ✅ Can use for: `WHERE merchant_id = ?`
- ✅ Can use for: `WHERE merchant_id = ? AND status = ?`
- ❌ Cannot use for: `WHERE status = ?` alone (use the separate `idx_orders_status` for that)

```sql
CREATE INDEX idx_orders_expires_at ON orders(expires_at) WHERE status = 'CREATED';
```

**🆕 PARTIAL INDEX — NEW CONCEPT**

A **partial index** only includes rows that match the `WHERE` condition. It's smaller and faster than a full index.

```
FULL INDEX (all rows):
  Indexes ALL orders: CREATED, ATTEMPTED, PAID, EXPIRED
  Size: 100,000 rows indexed

PARTIAL INDEX (only CREATED):
  Indexes ONLY orders with status='CREATED'
  Size: 5,000 rows indexed (much smaller!)
```

**WHY PARTIAL?** The expiry query is:
```sql
SELECT * FROM orders WHERE status = 'CREATED' AND expires_at < NOW();
```

Only CREATED orders can expire. PAID/EXPIRED orders are already done. A partial index skips them entirely → smaller index → faster query.

**THIS IS AN ADVANCED POSTGRESQL FEATURE** — not available in MySQL or H2. One of the reasons PayFlow uses PostgreSQL.

## 4. Step-by-Step: V2 — Payments Table

**File:** `src/main/resources/db/migration/V2__create_payments_table.sql`

### Line-by-Line

```sql
-- V2: Create payments table
-- Stores payment attempts and their lifecycle states

CREATE TABLE IF NOT EXISTS payments (
    id                  VARCHAR(30)     PRIMARY KEY,
    order_id            VARCHAR(30)     NOT NULL,
    merchant_id         VARCHAR(30)     NOT NULL,
    amount              NUMERIC(19, 4)  NOT NULL,
    currency            VARCHAR(3)      NOT NULL,
    status              VARCHAR(20)     NOT NULL DEFAULT 'CREATED',
    payment_method      VARCHAR(20)     NOT NULL,
```

`payment_method` stores: `"CARD"`, `"UPI"`, `"NET_BANKING"`, `"WALLET"`.

```sql
    authorization_code  VARCHAR(50),
    bank_reference_id   VARCHAR(100),
    failure_reason      VARCHAR(500),
```

**ALL THREE ARE NULLABLE** — they're populated at different stages:

| Field | Set When | Example |
|---|---|---|
| `authorization_code` | Bank approves (`AUTHORIZED`) | `"AUTH-847291"` |
| `bank_reference_id` | Bank returns reference | `"BNK-TXN-20240115-847291"` |
| `failure_reason` | Bank declines (`FAILED`) | `"Insufficient funds"` |

If status is `CREATED` → all three are null. If `AUTHORIZED` → code + reference set, reason null. If `FAILED` → only reason set.

```sql
    created_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_payments_order FOREIGN KEY (order_id) REFERENCES orders(id)
);
```

**FK TO ORDERS — BUT NO `ON DELETE CASCADE`**

| Merchant migrations | Payment migrations |
|---|---|
| `ON DELETE CASCADE` | No CASCADE |

**WHY NO CASCADE?**
```
Merchant: Delete merchant → delete all their API keys (OK, they're gone)

Payment: Delete order → delete all payments? NEVER!
  Payment records are financial evidence.
  Deleting them would violate audit requirements.
  Orders and payments are NEVER deleted — only status changes.
```

In a payment system, **nothing is ever deleted**. Records live forever for auditing, compliance, and dispute resolution.

**WHAT HAPPENS IF YOU TRY TO DELETE AN ORDER?**
```sql
DELETE FROM orders WHERE id = 'order_abc';
-- ERROR: update or delete on table "orders" violates foreign key constraint
-- "fk_payments_order" on table "payments"
```

The FK prevents deletion. This is intentional — it's a safety guardrail.

### Indexes

```sql
CREATE INDEX idx_payments_order_id ON payments(order_id);
```

**Query:** "Find all payment attempts for this order" → `WHERE order_id = ?`
This is the most common payment lookup — given an order, find its payment(s).

```sql
CREATE INDEX idx_payments_merchant_id ON payments(merchant_id);
```

**Query:** "List all payments for this merchant" → `WHERE merchant_id = ?` (dashboard)

```sql
CREATE INDEX idx_payments_merchant_status ON payments(merchant_id, status);
```

**Composite index** — same concept as orders. For: "Show all CAPTURED payments for merchant X" → `WHERE merchant_id = ? AND status = 'CAPTURED'`

This query is used by the settlement service to calculate how much to pay each merchant.

```sql
CREATE INDEX idx_payments_status ON payments(status);
```

**Query:** "Find all AUTHORIZED payments" (for batch capture/void operations) → `WHERE status = 'AUTHORIZED'`

## 5. Step-by-Step: V3 — Payment Methods Table

**File:** `src/main/resources/db/migration/V3__create_payment_methods_table.sql`

### Line-by-Line

```sql
-- V3: Create payment_methods table
-- Stores masked/tokenized payment method details per payment

CREATE TABLE IF NOT EXISTS payment_methods (
    id                  BIGSERIAL       PRIMARY KEY,
```

**🆕 `BIGSERIAL` — NEW CONCEPT**

| Type | What It Does | Java Equivalent |
|---|---|---|
| `UUID` | Random 128-bit identifier | `@GeneratedValue(UUID)` + `UUID id` |
| `VARCHAR(30)` | String set by application | No `@GeneratedValue` + `String id` |
| **`BIGSERIAL`** | **Auto-increment: 1, 2, 3, 4...** | `@GeneratedValue(IDENTITY)` + `Long id` |

`BIGSERIAL` = `BIGINT` + automatic sequence. PostgreSQL generates the next number on each INSERT.

**WHY BIGSERIAL HERE?**
PaymentMethodEntity is an internal detail — its ID is never exposed to clients. Simple auto-increment is sufficient. No need for fancy prefixed IDs.

```sql
    payment_id          VARCHAR(30)     NOT NULL,
    type                VARCHAR(20)     NOT NULL,
```

`payment_id` links to the payment this method belongs to. `type` is `"CARD"`, `"UPI"`, or `"NET_BANKING"`.

```sql
    card_last4          VARCHAR(4),
    card_brand          VARCHAR(20),
    card_expiry_month   VARCHAR(2),
    card_expiry_year    VARCHAR(4),
    upi_id              VARCHAR(100),
    bank_code           VARCHAR(20),
    bank_name           VARCHAR(100),
```

**ALL NULLABLE** — only the relevant fields are populated based on `type`:

```
type = "CARD":        card_last4="4242", card_brand="VISA", card_expiry_month="12", card_expiry_year="2025"
type = "UPI":         upi_id="customer@oksbi"
type = "NET_BANKING": bank_code="HDFC", bank_name="HDFC Bank"
```

**🔒 PCI NOTE:** `card_last4` is ALWAYS 4 digits or less. We NEVER store:
- Full card number (PAN) — PCI violation
- CVV — NEVER stored, not even temporarily
- Full card number hash — still considered cardholder data

```sql
    CONSTRAINT fk_payment_methods_payment FOREIGN KEY (payment_id) REFERENCES payments(id)
);
```

FK to payments — no CASCADE (same reason: never delete payment records).

```sql
CREATE INDEX idx_payment_methods_payment_id ON payment_methods(payment_id);
```

**Query:** "Find the payment method for this payment" → `WHERE payment_id = ?`
This is a 1:1 lookup — each payment has exactly one payment method record.

### No Timestamps

Notice: **no `created_at` or `updated_at`** columns. Payment methods are:
- Created once (when payment is authorized)
- Never modified
- Never queried by time

## 6. Step-by-Step: V4 — Refunds Table

**File:** `src/main/resources/db/migration/V4__create_refunds_table.sql`

### Line-by-Line

```sql
-- V4: Create refunds table
-- Stores refunds issued against captured payments (full and partial)

CREATE TABLE IF NOT EXISTS refunds (
    id              VARCHAR(30)     PRIMARY KEY,
    payment_id      VARCHAR(30)     NOT NULL,
    merchant_id     VARCHAR(30)     NOT NULL,
    amount          NUMERIC(19, 4)  NOT NULL,
    reason          VARCHAR(500),
    status          VARCHAR(20)     NOT NULL DEFAULT 'PROCESSED',
```

**`DEFAULT 'PROCESSED'`** — refunds are immediately processed in this implementation (no pending state).

```sql
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
```

**🆕 NO `updated_at` COLUMN**

| Table | Has updated_at? | Why |
|---|---|---|
| orders | ✅ Yes | Status changes (CREATED→ATTEMPTED→PAID) |
| payments | ✅ Yes | Status changes (CREATED→AUTHORIZED→CAPTURED) |
| payment_methods | ❌ No | Never modified after creation |
| **refunds** | **❌ No** | **Immutable financial records — never modified** |

Refunds are **append-only**. Once created, a refund record never changes. If something goes wrong, you create a NEW refund record, not modify the old one. This is standard practice in financial systems for audit trail integrity.

```sql
    CONSTRAINT fk_refunds_payment FOREIGN KEY (payment_id) REFERENCES payments(id)
);

CREATE INDEX idx_refunds_payment_id ON refunds(payment_id);
CREATE INDEX idx_refunds_merchant_id ON refunds(merchant_id);
```

**Two indexes:**
1. `payment_id` — "Find all refunds for this payment" (to calculate total refunded amount)
2. `merchant_id` — "List all refunds for this merchant" (dashboard/reports)

## 7. How Tables Relate (FK Chain)

```
┌──────────────────────────────────────────────────────────────┐
│                     FOREIGN KEY CHAIN                        │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  orders (V1)                                                 │
│    └── payments (V2)  FK: order_id → orders.id              │
│          ├── payment_methods (V3)  FK: payment_id → payments.id  │
│          └── refunds (V4)  FK: payment_id → payments.id     │
│                                                              │
│  MIGRATION ORDER MATTERS:                                    │
│  V1 first (orders — no FK deps)                             │
│  V2 second (payments → references orders)                   │
│  V3 third (payment_methods → references payments)           │
│  V4 fourth (refunds → references payments)                  │
│                                                              │
│  NONE USE ON DELETE CASCADE:                                 │
│  Financial records are NEVER deleted.                        │
│  FK exists only for referential integrity (prevent orphans). │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 8. Index Strategy Explained

### All 11 Indexes at a Glance

| Table | Index | Type | Query It Speeds Up |
|---|---|---|---|
| orders | `idx_orders_merchant_id` | Single | "Show orders for merchant X" |
| orders | `idx_orders_status` | Single | "Find all CREATED orders" |
| orders | `idx_orders_merchant_status` | **Composite** | "Show PAID orders for merchant X" |
| orders | `idx_orders_expires_at` | **Partial** | "Find expired CREATED orders" |
| payments | `idx_payments_order_id` | Single | "Find payments for order X" |
| payments | `idx_payments_merchant_id` | Single | "Show payments for merchant X" |
| payments | `idx_payments_merchant_status` | **Composite** | "Show CAPTURED payments for merchant X" |
| payments | `idx_payments_status` | Single | "Find all AUTHORIZED payments" |
| payment_methods | `idx_payment_methods_payment_id` | Single | "Find method for payment X" |
| refunds | `idx_refunds_payment_id` | Single | "Find refunds for payment X" |
| refunds | `idx_refunds_merchant_id` | Single | "Show refunds for merchant X" |

### Comparison: Merchant vs Payment Indexes

| Feature | Merchant (4 tables, 8 indexes) | Payment (4 tables, 11 indexes) |
|---|---|---|
| Single-column indexes | ✅ Yes | ✅ Yes |
| Composite indexes | ❌ None | ✅ 2 composite: (merchant_id, status) |
| Partial indexes | ❌ None | ✅ 1 partial: expires_at WHERE status='CREATED' |
| Why more? | Lower traffic, simple queries | Higher traffic, complex dashboard + expiry queries |

## 9. What You Learned

| # | Concept | Key Takeaway |
|---|---------|-------------|
| 1 | **VARCHAR(30) PRIMARY KEY** | String IDs for prefixed payment IDs (not UUID) |
| 2 | **NUMERIC(19,4)** | High-precision decimal for payment amounts (same as DECIMAL in PostgreSQL) |
| 3 | **CREATE TABLE IF NOT EXISTS** | Safety net — doesn't error if table already exists |
| 4 | **Partial index** | `WHERE status = 'CREATED'` — only indexes relevant rows, smaller + faster |
| 5 | **Composite index** | `(merchant_id, status)` — two-column index for combined WHERE conditions |
| 6 | **Column order in composite index** | Left-to-right: `(A, B)` works for `WHERE A=?` and `WHERE A=? AND B=?`, NOT for `WHERE B=?` alone |
| 7 | **BIGSERIAL** | PostgreSQL auto-increment for Long IDs (payment_methods internal table) |
| 8 | **No ON DELETE CASCADE** | Financial records are NEVER deleted — FK prevents deletion as a safety guardrail |
| 9 | **No updated_at on refunds** | Immutable records — financial audit trail must be append-only |
| 10 | **No FK to merchant_id** | Cross-database FKs don't exist — application code enforces consistency |
| 11 | **TIMESTAMPTZ** | Short for TIMESTAMP WITH TIME ZONE — stores UTC |
| 12 | **DEFAULT 'CREATED'** | Initial state set by DB if application doesn't provide it |
| 13 | **11 indexes total** | More than merchant (8) — payment queries are more complex and higher traffic |
