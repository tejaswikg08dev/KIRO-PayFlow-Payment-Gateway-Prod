| **RefundService** | Event publishing, BigDecimal math, state validation | Same event pattern, same state checking |

```java
// In common-lib/src/main/java/com/payflow/common/util/IdGenerator.java:
public static String generateOrderId() {
    return "order_" + shortUuid();  // "order_7a3f9b2c1d4e"
}
private static String shortUuid() {
    return UUID.randomUUID().toString().replace("-", "").substring(0, 12);
```

**WHY SET ID IN CODE (not @GeneratedValue)?**
- Prefixed IDs (`order_abc`) can't be generated by PostgreSQL or Hibernate
- We control the format: `"order_"` prefix + 12 hex chars
- The ID is known BEFORE the INSERT — can be logged, returned immediately

**COMPARISON:**

| Service | ID Generation | Example |
|---|---|---|
| Identity | `@GeneratedValue(UUID)` — Hibernate generates | `"a1b2c3d4-e5f6-..."` |
| Merchant | `@GeneratedValue(UUID)` — Hibernate generates | `UUID("a1b2c3d4-...")` |
| **Payment** | **`IdGenerator.generateOrderId()`** — code generates | `"order_7a3f9b2c1d4e"` |

**🆕 TTL — 30-MINUTE EXPIRY**

```java
Instant.now()                     // "2024-01-15T10:30:00Z"
  .plus(30, ChronoUnit.MINUTES)  // "2024-01-15T11:00:00Z"
```

This order can only be paid within 30 minutes. After that, `expireOrders()` marks it EXPIRED.

**WHY 30 MINUTES?**
- Too short (5 min): Customer can't complete checkout
- Too long (24 hours): Price changes, inventory issues, fraud risk
- 30 min: Industry standard (Razorpay, Stripe checkout sessions)

### Method: expireOrders

```java
    @Transactional
    public int expireOrders() {
        List<Order> createdOrders = orderRepository.findByStatus(OrderStatus.CREATED);
        int expired = 0;

        for (Order order : createdOrders) {
            if (order.getExpiresAt() != null && order.getExpiresAt().isBefore(Instant.now())) {
                order.setStatus(OrderStatus.EXPIRED);
                orderRepository.save(order);
                expired++;
                log.info("Order expired: {}", order.getId());
            }
        }

        log.info("Expired {} orders", expired);
        return expired;
    }
```

**🆕 BULK STATUS UPDATE — NEW PATTERN**

This method:
1. Fetches ALL orders with status `CREATED`
2. For each, checks if `expiresAt` is in the past
3. If yes → sets status to `EXPIRED` and saves
4. Returns the count of expired orders

**WHO CALLS THIS?**
- An admin endpoint: `POST /v1/orders/expire`
- In production: a scheduled cron job (Spring `@Scheduled`)
- The partial index `idx_orders_expires_at WHERE status='CREATED'` optimizes step 1

**WHY NOT A SINGLE SQL UPDATE?**
```sql
-- This WOULD be more efficient:
UPDATE orders SET status = 'EXPIRED' WHERE status = 'CREATED' AND expires_at < NOW();
```

The Java approach is chosen for:
- Logging each expired order individually (audit trail)
- Potential future logic (notify merchant about expiry)
- Testability (mockable in unit tests)

### Methods: getOrderEntity + updateOrderStatus (Internal)

```java
    @Transactional(readOnly = true)
    public Order getOrderEntity(String orderId) {
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new ResourceNotFoundException("Order", orderId));
    }

    @Transactional
    public void updateOrderStatus(String orderId, OrderStatus status) {
        Order order = getOrderEntity(orderId);
        order.setStatus(status);
        orderRepository.save(order);
        log.info("Order {} status updated to {}", orderId, status);
    }
```

**WHY TWO INTERNAL METHODS?**

| Method | Returns | Used By |
|---|---|---|
| `getOrderEntity()` | `Order` (entity) | PaymentService — needs the entity to check `expiresAt`, `status`, `amount` |
| `getOrder()` | `OrderResponse` (DTO) | Controller — returns JSON to client |
| `updateOrderStatus()` | void | PaymentService — after capture, update order to PAID |

**`getOrderEntity` returns the RAW ENTITY** (not a DTO). This is an internal method — PaymentService needs the entity to read its fields and make business decisions. DTOs are only for external API responses.

### Method: createRefund (THE CRITICAL METHOD)

This is the most business-logic-heavy method in the simpler services. Let's trace every step:

```java
    @Transactional
    public RefundResponse createRefund(RefundRequest request) {
        log.info("Creating refund for payment: {}, amount: {}", 
                request.getPaymentId(), request.getAmount());
```

```java
        // 1. Validate payment exists and is captured
        Payment payment = paymentRepository.findById(request.getPaymentId())
                .orElseThrow(() -> new ResourceNotFoundException("Payment", request.getPaymentId()));

        if (payment.getStatus() != PaymentStatus.CAPTURED) {
            throw new PayflowException("INVALID_STATE",
                    String.format("Cannot refund payment in status: %s. Must be CAPTURED.", 
                            payment.getStatus()));
        }
```

**STATE VALIDATION:**
```
Can refund:    CAPTURED    ✅
Can't refund:  CREATED     ❌ (not yet processed)
Can't refund:  AUTHORIZED  ❌ (use void instead)
Can't refund:  VOIDED      ❌ (already cancelled)
Can't refund:  FAILED      ❌ (never charged)
Can't refund:  REFUNDED    ❌ (already fully refunded)
```

`PayflowException` with code `"INVALID_STATE"` is caught by the exception handler → returns HTTP 422 Unprocessable Entity.

```java
        // 2. Calculate total already refunded
        List<Refund> existingRefunds = refundRepository.findByPaymentId(payment.getId());
        BigDecimal totalRefunded = existingRefunds.stream()
                .map(Refund::getAmount)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
```

**🆕 BIGDECIMAL STREAM SUM — NEW PATTERN**

```java
// What this does step by step:
existingRefunds = [Refund(300), Refund(200)]  // previous partial refunds

existingRefunds.stream()           // Stream<Refund>
  .map(Refund::getAmount)          // Stream<BigDecimal>: [300, 200]
  .reduce(BigDecimal.ZERO,         // Start with 0
          BigDecimal::add);        // Add each: 0 + 300 + 200 = 500

totalRefunded = 500
```

**WHY `BigDecimal::add` NOT `+` OPERATOR?** BigDecimal doesn't support `+`. You must use `.add()`:
```java
// ❌ BigDecimal doesn't support +
total = amount1 + amount2;  // Compilation error!

// ✅ Use .add()
total = amount1.add(amount2);
```

```java
        BigDecimal remainingRefundable = payment.getAmount().subtract(totalRefunded);
```

**OVER-REFUND PREVENTION MATH:**
```
Payment amount:    ₹1,000
Already refunded:  ₹500 (from previous refunds)
Remaining:         ₹1,000 - ₹500 = ₹500

Now requesting:    ₹600
₹600 > ₹500? → YES → REJECT!
```

```java
        // 3. Validate refund amount
        if (request.getAmount().compareTo(remainingRefundable) > 0) {
            throw new PayflowException("REFUND_EXCEEDS_LIMIT",
                    String.format("Refund amount %.4f exceeds remaining refundable amount %.4f",
                            request.getAmount(), remainingRefundable));
        }
```

**`compareTo` for BigDecimal comparison:**
```java
a.compareTo(b) > 0   // a > b
a.compareTo(b) == 0   // a == b
a.compareTo(b) < 0    // a < b

// ❌ Never use == or > with BigDecimal
// new BigDecimal("1.0").equals(new BigDecimal("1.00")) → false! (different scale)
// Always use compareTo()
```

```java
        // 4. Create the refund
        Refund refund = Refund.builder()
                .id(IdGenerator.generateRefundId())
                .paymentId(payment.getId())
                .merchantId(payment.getMerchantId())
                .amount(request.getAmount())
                .reason(request.getReason())
                .status("PROCESSED")
                .build();

        refund = refundRepository.save(refund);
```

Generates prefixed ID: `"rfnd_9c5d3e2f4a6b"`. Status is immediately `"PROCESSED"` (no pending state in this implementation).

```java
        // 5. If fully refunded, update payment status
        BigDecimal newTotalRefunded = totalRefunded.add(request.getAmount());
        if (newTotalRefunded.compareTo(payment.getAmount()) >= 0) {
            payment.setStatus(PaymentStatus.REFUNDED);
            paymentRepository.save(payment);
            log.info("Payment fully refunded: {}", payment.getId());
        }
```

**🆕 CONDITIONAL STATUS CHANGE:**
```
Scenario 1 — Partial refund:
  Payment: ₹1,000
  This refund: ₹300
  Total refunded after: ₹300
  ₹300 < ₹1,000 → payment stays CAPTURED (can still refund ₹700 more)

Scenario 2 — Final refund (becomes fully refunded):
  Payment: ₹1,000
  Previous refunds: ₹700
  This refund: ₹300
  Total refunded after: ₹1,000
  ₹1,000 >= ₹1,000 → payment → REFUNDED (no more refunds possible)
```

```java
        // 6. Publish refund event
        publishRefundEvent(payment, refund);

        log.info("Refund created: {} for payment: {}", refund.getId(), payment.getId());
        return toRefundResponse(refund);
    }
```

### Private Helper: publishRefundEvent

```java
    private void publishRefundEvent(Payment payment, Refund refund) {
        try {
            PaymentEvent event = PaymentEvent.builder()
                    .eventId(IdGenerator.generateEventId())
                    .eventType("payment.refunded")
                    .paymentId(payment.getId())
                    .orderId(payment.getOrderId())
                    .merchantId(payment.getMerchantId())
                    .amount(refund.getAmount())
                    .currency(payment.getCurrency())
                    .status("REFUNDED")
                    .paymentMethod(payment.getPaymentMethod().name())
                    .timestamp(Instant.now())
                    .metadata(refund.getId())
                    .build();

            eventPublisher.publishPaymentEvent("payment.refunded", event);
        } catch (Exception e) {
            log.error("Failed to publish refund event for refund: {}", refund.getId(), e);
        }
    }
```

**🆕 FIRE-AND-FORGET EVENT PATTERN:**

```
try {
    eventPublisher.publishPaymentEvent(...);  // Send to Kafka
} catch (Exception e) {
    log.error(...);  // Log the failure
    // DO NOT re-throw! The refund is already saved in DB.
    // Kafka being down should NOT undo a successful refund.
}
```

**WHY CATCH ALL EXCEPTIONS?**
- The refund is already saved to PostgreSQL (permanent)
- If Kafka is down, the event is lost — but the refund happened
- Retry mechanisms or event replay can recover lost events later
- Rolling back a refund because Kafka is unavailable is WORSE than losing an event

**`PaymentEvent` from common-lib** — the standardized event format all services publish:

| Field | Value | Purpose |
|---|---|---|
| `eventId` | `"evt_abc123"` | Unique event identifier |
| `eventType` | `"payment.refunded"` | What happened |
| `paymentId` | `"pay_xyz"` | Which payment |
| `orderId` | `"order_def"` | Which order |
| `merchantId` | `"mer_ghi"` | Which merchant (for webhook routing) |
| `amount` | `300.00` | Refund amount (not payment amount!) |
| `metadata` | `"rfnd_jkl"` | Extra data (refund ID in this case) |


**Always use `isEqualByComparingTo` for BigDecimal assertions.**

## 6. What You Learned

| # | Concept | Key Takeaway |
|---|---------|-------------|
| 1 | **IdGenerator.generateOrderId()** | Prefixed IDs set in code, not by Hibernate — `"order_7a3f9b2c1d4e"` |
| 2 | **30-minute TTL** | `Instant.now().plus(30, ChronoUnit.MINUTES)` — order expires after 30 min |
| 3 | **expireOrders()** | Bulk status update CREATED→EXPIRED for past-due orders |
| 4 | **getOrderEntity vs getOrder** | Entity for internal use (PaymentService), DTO for external API |
| 5 | **State validation** | Only CAPTURED payments can be refunded — checked before processing |
| 6 | **Over-refund prevention** | Sum existing refunds → calculate remaining → reject if exceeded |
| 7 | **BigDecimal stream sum** | `.stream().map(::getAmount).reduce(ZERO, BigDecimal::add)` |
| 8 | **compareTo for BigDecimal** | Never use `==` or `>` — always `a.compareTo(b) > 0` |
| 9 | **isEqualByComparingTo** | AssertJ assertion for BigDecimal that ignores scale |
| 10 | **Conditional status change** | Payment → REFUNDED only when totalRefunded >= paymentAmount |
| 11 | **Fire-and-forget events** | Catch exceptions from eventPublisher — never fail a refund because Kafka is down |
| 12 | **PaymentEvent from common-lib** | Standardized event format: eventId, eventType, paymentId, amount, etc. |
| 13 | **Manual DTO mapping** | RefundService uses builder directly — no MapStruct for 7 matching fields |
| 14 | **toUpperCase() normalization** | Currency code `"inr"` → `"INR"` — defensive coding |
